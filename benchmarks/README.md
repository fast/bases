# Codec benchmarks

Run the same fixed workload for every implementation in a scenario. The results give elapsed milliseconds for a batch of messages. Compare times within one row, since each row can select a different round count.

| Workload             | Raw message sizes              | Work per round                                                   | Peers                                                                                                  |
| -------------------- | ------------------------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Caller buffers       | 8 B, 32 B, 64 B, 1 KiB, 16 KiB | Encode or decode into a reusable byte slice.                     | `data-encoding`, `hex`, `faster-hex`, `const-hex`, RustCrypto, `base64`, `base64::Simd`, `base64-simd` |
| Owned output         | 8 B, 32 B, 1 KiB               | Return and drop a fresh string or byte vector for each message.  | `data-encoding`, `hex`, `const-hex`, `base16ct`, `base32ct`, `base64`, `base64::Simd`, `base64-simd`   |
| Display              | 32 B, 1 KiB                    | Format lowercase hex or padded Base64 into a reused string.      | `data-encoding`, `base16ct`, `base64`, `base64::Simd`                                                  |
| Streaming Base64     | 16 KiB                         | Process chunks of at most 257 bytes into a fixed destination.    | `base64` I/O adapters with general-purpose and SIMD engines                                            |
| Invalid Base64 input | 1 KiB before encoding          | Reject `!` at the first or last data symbol of a padded message. | `data-encoding`, `base64`, `base64::Simd`, `base64-simd`                                               |

All families have caller-buffer cases at 8 B, 32 B, 1 KiB and 16 KiB; Base64 also includes 64 B. Base32 adds 159 B, 160 B and 164 B to cover the scalar bulk threshold and a partial quantum above it. These cases use normal CPU dispatch, so exercising the bulk scalar path requires a scalar build. This separates short-field overhead from bulk throughput. Owned workloads cover a 32-byte hex field, 1 KiB of padded Base32 or Base64, and an 8-byte unpadded URL-safe cursor. Owned decoders receive a string. Streaming includes finalization or reading to EOF, including the I/O adapter's buffering. The invalid-input cases check acceptance of the original message before corrupting one symbol.

```shell
cargo x bench --no-run
cargo x bench -- --list
cargo x bench -- --test
cargo x bench -- --repeat 5 --raw
cargo x bench -- base64/stream --repeat 5 --raw
```

Following [Benchmark In Milliseconds](https://matklad.github.io/2026/10/05/benchmark-milliseconds.html), choose fixed round counts that take roughly 300 ms on the reference implementation. To size a new case, use `--baseline-only --rounds N`. Keep the counts fixed across peers and revisions.

Each scenario prepares a deterministic input and a known output before timing and reuses them across samples. Each timed sample runs all rounds, checks the result and drops its output buffers. Sample bookkeeping keeps the same allocation layout when selecting only `bases`. The runner interleaves peers, rotates the starting order and reports the median and full range in integer milliseconds. `--raw` includes the first sample and every outlier. The elapsed-time ratio uses unrounded medians relative to `bases`, so `0.80x` means 20% less time for the same work. CI uses `--test` to verify the bytes or rejection once per case.

For native Linux measurements, run `bash benchmarks/linux.sh <base-revision> <results-directory>` on a dedicated machine; it requires Rust, Git, `jq` and `taskset`. Run it from a clean repository root with the baseline commit available locally and choose a results directory outside the repository. The script records the CPU model, OS, compiler, lockfile hash and raw samples in that directory. It builds both library revisions with the current benchmark harness, workspace settings and lockfile, verifies each workload, then pins measurements to one allowed CPU. Five before/after samples alternate their order per scenario; a separate five-sample pass compares ecosystem peers. Each scenario runs in a fresh process through the same executable path to keep invocation-dependent setup consistent. Shared-host scheduling and CPU frequency can still affect results, so inspect sample ranges and repeat on production-class hardware before setting performance thresholds.

Base16 cases use lowercase output (`Base16Lower` and `HEXLOWER_PERMISSIVE`) because `hex::encode_to_slice` emits lowercase hex only. `faster-hex` is compared on caller-provided slice buffers (`hex_encode` and `hex_decode`) rather than `Vec`-returning owned decode because it exposes slice-buffer decoding without a first-party `Vec`-returning decode helper, whereas `hex` and `const-hex` appear in both caller-buffer and owned Base16 rows. The `base64` label denotes its general-purpose engine; `base64::Simd` denotes its runtime-selected SIMD engine on x86_64 and AArch64, constructed once per scenario outside the timed samples. The separate `base64-simd` crate uses its default CPU dispatch. RustCrypto's `base16ct`, `base32ct` and `base64ct` target best-effort constant-time operation, which Bases does not promise. The rejection benchmarks include each library's error-reporting work: Bases returns the first invalid byte and its offset, whereas `base64-simd` returns an opaque error. Valid-input rows use the same wire bytes for all peers. They measure neither the full malformed-input policies nor timing side channels; for example, `data-encoding` accepts concatenated padded blocks that Bases rejects. Record the CPU, compiler, feature flags and locked dependency versions when sharing results, and compare repeated samples on the same machine.
